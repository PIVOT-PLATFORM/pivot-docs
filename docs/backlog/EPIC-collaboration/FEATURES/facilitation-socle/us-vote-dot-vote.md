# US08.12.2 — Vote / dot-vote (facilitation)

**En tant que** participant à un atelier collaboratif
**Je veux** qu'un owner/éditeur ouvre puis clôture une session de vote (dot-vote), et que chaque votant autorisé puisse déposer et retirer ses votes sur les cartes dans la limite d'un quota
**Afin de** prioriser collectivement des idées sur le tableau, sans qu'un votant puisse dépasser son quota même en cas de clic concurrent, ni voter après l'expiration du minuteur de vote

## Critères d'acceptation

| Critère | 🤖 Dev |
|---------|--------|
| Given je suis owner ou éditeur, when j'envoie `vote:start` `{boardId, votesPerPerson, timerSeconds, voterIds}`, then le serveur **ferme d'abord toute session `ACTIVE` existante** (`status → CLOSED`, sans émettre `vote:session:closed` pour cette fermeture implicite), crée une nouvelle session (`votesPerPerson` défaut **3**, `voterIds`, `timerEndsAt = timerSeconds ? now + timerSeconds*1000 : null`, votes `[]`) et diffuse `vote:session:started` (session complète) à toute la room | ⬜ |
| Given une session de vote active avec `votesPerPerson=3` et l'utilisateur U dans `voterIds`, when U envoie `vote:cast` `{sessionId, boardId, cardId}` alors qu'il a déjà 2 votes, then le 3ᵉ vote est enregistré et `vote:updated` (session complète refetchée) est diffusé à toute la room | ⬜ |
| Given U a déjà consommé ses 3 votes, when il tente un 4ᵉ `vote:cast`, then la garde de quota (transaction **Serializable** : `count(votes de U dans la session) < votesPerPerson` puis `create` dans la même transaction) constate `3 >= 3` et n'insère rien ; aucun `vote:updated` n'est émis pour cette tentative | ⬜ |
| Given U a 2 votes sur 3, when il envoie deux `vote:cast` quasi simultanés (double-clic) pour deux cartes différentes, then une seule transaction gagne la sérialisation Postgres, l'autre lève un conflit de sérialisation **catché silencieusement** (pas de retry, pas d'erreur au client), et U se retrouve avec **exactement 3 votes au total (jamais 4)** | ⬜ |
| Given U n'a pas encore voté (quota 3), when U vote 2 fois pour **la même carte X**, then les 2 votes sont acceptés (aucune contrainte d'unicité par carte — seul le total par personne est plafonné) ; un `vote:uncast` `{sessionId, boardId, cardId}` retire **un seul** de ces votes (`findFirst` puis `delete`, jamais `deleteMany`), laissant l'autre en place | ⬜ |
| Given une session avec `timerEndsAt` dans le passé selon l'**horloge serveur**, when un client dont l'horloge est en retard (compte à rebours encore positif à l'écran) envoie `vote:cast`, then le serveur refuse silencieusement (comparaison `timerEndsAt` contre sa propre horloge, jamais celle du client) | ⬜ |
| Given une session de vote active avec `timerEndsAt` non null, when un owner/éditeur envoie `vote:extend` `{sessionId, boardId, extraSeconds}`, then le nouveau `timerEndsAt = max(timerEndsAt actuel, now) + extraSeconds*1000` — base = `max(timerEndsAt, now)` de sorte qu'un timer de vote expiré redonne réellement `extraSeconds` de temps utile ; `vote:updated` diffusé. Si `timerEndsAt` est null → no-op silencieux | ⬜ |
| Given une session de vote existante, when un owner/éditeur envoie `vote:stop` `{sessionId, boardId}`, then le serveur clôture la session (`status → CLOSED`, `closedAt`) **après avoir vérifié qu'elle existe et qu'elle est `ACTIVE`** (correctif §6.7 : garde sur session manquante ET sur statut, pour ne pas re-clôturer une session déjà fermée ni planter sur un `sessionId` inexistant), puis diffuse `vote:session:closed` (session complète) à toute la room | ⬜ |
| Given une carte ayant reçu des votes, when cette carte est supprimée, then les votes correspondants ne restent **pas orphelins** : une décision d'intégrité est appliquée (correctif §6.8/§6.9 : relation formelle `BoardVote.cardId → Card` avec `onDelete: Cascade`, alignée sur `CardConnection`/`CardFieldValue`) et un `vote:updated` est diffusé pour refléter le nouveau décompte de votes | ⬜ |
| Given un `vote:start`, when la session est ouverte, then chaque carte du tableau expose un décompte de votes agrégé (nombre de votes reçus, éventuellement par votant selon l'UI) recalculé à chaque `vote:updated` — la source de vérité est le refetch serveur de la session, pas un compteur optimiste client | ⬜ |
| Error : given un `vote:stop` avec un `sessionId` inexistant, when le serveur le reçoit, then il est traité comme un no-op silencieux (garde d'existence, cf. correctif §6.7) — aucune exception P2025 non catchée ne remonte au client, contrairement au comportement défectueux du POC de référence | ⬜ |
| Error : given un `vote:cast` par un utilisateur **absent de `voterIds`**, ou anonyme sans compte (userId absent), ou sur une session non `ACTIVE`, when le serveur le reçoit, then il refuse silencieusement (chaîne de gardes : userId requis → session existe et `ACTIVE` → `timerEndsAt` non expiré → `userId ∈ voterIds`) — aucun vote, aucune diffusion, aucune erreur dédiée | ⬜ |
| Security : `boardId`, `sessionId` et l'identité utilisateur/tenant sont résolus depuis le SecurityContext (token opaque) + l'appartenance à la room — jamais depuis le body brut ; le serveur ne fait jamais confiance à un `userId` fourni par le client pour attribuer un vote | ⬜ |
| Security : `vote:start`/`vote:stop`/`vote:extend` sont gardés `canWrite` (OWNER+EDITOR) ; `vote:cast`/`vote:uncast` sont gardés `canAccess` (tout rôle **y compris VIEWER**, un VIEWER peut voter s'il est dans `voterIds`) — un rôle insuffisant est refusé silencieusement (§3.12) | ⬜ |
| Security : le quota est appliqué **en base** dans une transaction Serializable (pas seulement côté client), de sorte qu'un client modifié / une race ne permet jamais de dépasser `votesPerPerson` ; le contrôle d'expiration du timer de vote est fait contre l'horloge **serveur** (un client à l'horloge trafiquée ne peut voter après échéance) | ⬜ |
| A11y : les boutons voter/retirer sur chaque carte portent un `aria-label` explicite incluant le décompte courant (ex. « Voter pour [titre] — 2 votes »), l'état quota-atteint est annoncé (bouton `disabled` + `aria-disabled` + message `aria-live="polite"`), et le compte à rebours de la session de vote est exposé via `role="timer"` `aria-live="polite"` | ⬜ |
| Tests TI : `vote:start` (owner/editor → session créée + fermeture implicite de l'ACTIVE précédente sans `vote:session:closed`, viewer → refus) ; `vote:cast` quota (3ᵉ OK, 4ᵉ refusé, race Serializable → jamais 4 votes) ; multiple votes même carte + `vote:uncast` retire un seul ; `vote:cast` après `timerEndsAt` serveur → refus ; `vote:cast` hors `voterIds` → refus ; **`vote:stop` sur session inexistante → no-op (correctif §6.7)** ; **suppression d'une carte votée → votes supprimés en cascade, pas d'orphelins (correctif §6.9)** | ⬜ |
| Tests Vitest : ouverture/clôture session côté UI, décompte de votes par carte recalculé sur `vote:updated`, bouton voter désactivé au quota atteint, retrait d'un vote, VIEWER autorisé à voter s'il est dans `voterIds`, compte à rebours de session synchronisé sur l'horloge serveur | ⬜ |

## Hors périmètre

- Vote pondéré (poids différents par votant) ou vote à choix unique/classement — hors scope, dot-vote à quota uniforme uniquement
- Anonymat des votes (masquer qui a voté quoi) — hors scope Socle ; la session stocke `userId` par vote, l'exposition ou non côté UI est une décision d'affichage non couverte ici
- Résultats / analytics de vote persistés au-delà de la session courante et de la dernière session `CLOSED` (`GET /:id/vote/last`, US de lecture) — pas d'agrégation historique multi-sessions
- Undo/redo du module vote — non couvert par l'historique (§4.5 du spec, décision reproduite) : `startVote`/`castVote`/`uncast`/`stop` ne sont pas annulables par Ctrl+Z
- Validation métier de `votesPerPerson > 0` et que `voterIds` correspondent à des membres réels : le POC de référence ne la fait pas (§3.11) ; en reproduction, une validation minimale (`votesPerPerson >= 1`, `voterIds` ⊆ membres du board) **peut** être ajoutée en implémentation mais n'est pas requise par cette US (à trancher au raffinage, non bloquant pour le Socle)

## Notes d'implémentation

- Backend `pivot-collaboratif-core` (traduction stack Node/Socket.io + Prisma → Spring + STOMP + Redis + JPA/Postgres) :
  - Entités `board_vote_session` (`id`, `board_id`, `status` enum `ACTIVE|CLOSED` défaut `ACTIVE`, `votes_per_person` défaut **3**, `timer_seconds` nullable, `timer_ends_at` nullable, `voter_ids` liste, `created_at`, `closed_at`) et `board_vote` (`id`, `session_id`, `card_id`, `user_id`, `created_at`)
  - **Correctif §6.9 (relation manquante)** : `board_vote.card_id` reçoit une **FK formelle vers `card` avec `onDelete: Cascade`** (le POC laissait `cardId` en String simple sans relation → votes orphelins à la suppression d'une carte). Alignement sur `card_connection`/`card_field_value` qui cascadent déjà (§1.9, §6.9)
  - `vote:start` : ferme toute session `ACTIVE` du board (`update ... status=CLOSED`) **sans** émettre `vote:session:closed` pour cette fermeture implicite (§3.11), puis crée la nouvelle session ; `timerEndsAt = timerSeconds != null ? now + timerSeconds*1000 : null`
  - `vote:cast` : chaîne de gardes silencieuses (userId requis → session `ACTIVE` → `timerEndsAt` non expiré selon l'**horloge serveur** → `userId ∈ voterIds`), puis **transaction isolation Serializable** : `count(votes de userId dans la session) < votesPerPerson` sinon abandon ; conflit de sérialisation → catch silencieux sans retry (§5.3). `vote:updated` (session refetchée) diffusé si succès
  - `vote:uncast` : mêmes gardes existence/ACTIVE/horloge ; `findFirst` du vote `(session, card, user)` puis `delete` d'**un seul** (jamais `deleteMany`), même si l'utilisateur a voté plusieurs fois pour cette carte (§3.11)
  - `vote:extend` : requiert `timerEndsAt` non null (sinon no-op) ; `base = max(timerEndsAt, now)` ; `nouveau timerEndsAt = base + extraSeconds*1000` (§3.11, §5.4)
  - **Correctif §6.7 (`vote:stop` non gardé)** : avant l'update, **vérifier que la session existe ET que `status == ACTIVE`** — sinon no-op silencieux. Corrige les deux défauts du POC : (a) `sessionId` inexistant → P2025 non catchée qui remontait au client, (b) re-clôture d'une session déjà `CLOSED`. Diffuse `vote:session:closed` (session complète) si effectif
  - Canal STOMP `/topic/board/{boardId}` ; gardes `canWrite` (start/stop/extend) et `canAccess` incl. VIEWER (cast/uncast) résolues depuis le SecurityContext + appartenance room (EN08.1)
  - Lecture (hors périmètre code de cette US, déjà tracé §2.6) : `GET /:id/vote/current` (session `ACTIVE` la plus récente) / `GET /:id/vote/last` (dernière `CLOSED`)
- Frontend `pivot-collaboratif-ui` : overlay de vote sur les cartes (pastilles / décompte), déclenché par `vote:session:started` ; décompte recalculé à chaque `vote:updated` depuis la session refetchée (pas de compteur optimiste divergent) ; boutons start/stop/extend visibles OWNER/EDITOR, boutons voter/retirer pour tout membre présent dans `voterIds`
- **Absorption US30.3.1 dans le Socle** : l'activité « Vote / dot-vote » précédemment cataloguée sous US30.3.1 (facilitation d'ateliers, hors Socle) est absorbée dans le Socle E08 au titre de la parité complète vs POC PouetPouet — décision mainteneur d'absorption intégrale du spec de référence
- **Défauts corrigés et signalés** vs POC de référence : §6.7 (`vote:stop` sans garde d'existence/statut → désormais gardé), §6.8/§6.9 (absence de contrainte/cascade sur `BoardVote` → FK `card_id` cascade ajoutée pour éviter les votes orphelins)
- i18n : clés `whiteboard.facilitation.vote.*` (fr.json / en.json)

## Spec fonctionnelle

### Ce que fait la fonctionnalité

Vue participant de l'activité Q&A d'une session live. Un participant (authentifié ou invité anonyme) :

1. **Soumet une question** — champ texte + case « anonyme » optionnelle. À l'envoi, le champ est vidé ; la question n'apparaît pas par écho local mais uniquement quand le broadcast `QUESTION_ADDED` revient (source de vérité unique = le serveur).
2. **Upvote une question** — un vote par question par participant. Le bouton passe en état `aria-pressed` et se verrouille localement ; le compteur affiché suit le broadcast `QUESTION_UPVOTED`. Un double-vote rejeté (`409`) laisse le bouton verrouillé (état cohérent) ; une erreur non-409 le déverrouille pour permettre un retry.
3. **Voit la liste triée en temps réel** — tri `upvotes décroissants`, puis `plus ancienne d'abord` en cas d'égalité. Le tri est un `computed` client recalculé à chaque événement.
4. Un **animateur** peut marquer une question `ANSWERED` — broadcast `QUESTION_ANSWERED`, badge « répondu » côté participant.

La liste est hydratée une fois via `GET .../qa/questions` ; si cette lecture est indisponible (ex. invité anonyme sans droit de lecture REST), la vue démarre vide et se peuple purement par les broadcasts WS — dégradation silencieuse, jamais d'erreur bloquante.

### Sécurité & accessibilité

| Propriété | Mécanisme |
|-----------|-----------|
| XSS | Texte de question rendu **exclusivement** par interpolation Angular `{{ }}` — jamais `innerHTML` |
| Pas de `$any` | Champs de saisie lus via template refs typées |
| Isolation tenant | Résolue côté backend depuis le token porteur — aucun `tenantId`/`userId` envoyé par le client |
| A11y | `aria-pressed` sur le bouton d'upvote · liste `aria-live="polite"` · `aria-describedby` sur l'erreur de saisie · `role="alert"` · nom accessible contextualisé (le texte de la question est passé en paramètre transloco au libellé du bouton) |

## Contrat technique final

Endpoint racine : `${collaboratifApiUrl}/sessions/{sessionId}`. Identité (userId/tenantId) résolue par le backend depuis le token porteur (auth) ou `X-Guest-Token` (invité) — jamais dans le body.

| Verbe | Chemin | Rôle | Corps |
|-------|--------|------|-------|
| `GET` | `/qa/questions` | participant | — → `QaQuestion[]` |
| `POST` | `/qa/questions` | participant | `{ text: string, anonymous: boolean }` → `204` |
| `POST` | `/qa/questions/{questionId}/upvote` | participant | — → `204` · double vote → `409` |
| `POST` | `/qa/questions/{questionId}/answered` | animateur | — → `204` |

### Broadcasts STOMP

Topic unique par session : `/topic/collaboratif/session/{sessionId}` (endpoint temps réel `collaboratif` partagé). Chaque message porte un `type` discriminant.

| Événement | Charge utile | Effet client |
|-----------|--------------|--------------|
| `QUESTION_ADDED` | question complète | insertion + re-tri |
| `QUESTION_UPVOTED` | `{ questionId, upvoteCount }` | maj compteur + re-tri |
| `QUESTION_ANSWERED` | `{ questionId }` | badge « répondu » |

### `QaQuestion`

```ts
{ id: string; text: string; authorName: string | null; anonymous: boolean;
  upvoteCount: number; answered: boolean; createdAt: string }
```
